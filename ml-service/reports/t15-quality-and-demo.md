## 4. Голосовые звонки: что проверено и чего утверждать нельзя

RU protected — короткая **вымышленная расшифровка**, channel=voice call. Все пять
реплик имеют один ISO timestamp с зоной `2026-11-07T10:00:00+05:00`, но разные
позиционные IDs. Порядок остаётся m0001…m0005; совпавшие timestamps не объединяют
клиента, бота, system и оператора. Событие m0003 означает соединение, не identity verification.

По тексту можно проверить явные действия/оскорбления, содержание и порядок реплик,
проверку личности перед действием, отсутствие заданного поведения и ясность слов.
Нельзя по этому fixture заявлять анализ дикции, интонации, тембра, пауз, акустической
разборчивости, эмоций по голосу, качества ASR или соответствия записи расшифровке.
Нельзя вывести audio offsets из абсолютного времени без recording origin.

Provider отправляет текстовые messages, не аудио. Evaluator для voice call добавляет
`AUDIO_NOT_ASSESSED`; сохранённый RU v3 содержит этот warning. Все результаты также
имеют `DOMAIN_FACT_UNVERIFIED`. Это честные ограничения, не выполненный audio analysis.
В этой работе не проверены audio playback и длинные контексты. Ошибка/неоднозначность
расшифровки сама по себе не доказывает нарушение. Для соответствующих пунктов T15
нужны отдельная разрешённая проверка входов/воспроизведения и явная область применимости.

## 6. Безопасность: demo остаётся вне обеих live policies

- **Python, проверено сейчас:** fingerprint новой conversation отсутствует в
  `synthetic_fingerprints()`. Функция читает только собственные tests/fixtures и
  опубликованные synthetic positive contracts; reports/ не сканируется. Собственных
  request fixtures ровно **6**. Для обеих версий demo нет разрешения на inference.
- **Java, проверено по исходникам:** SyntheticPolicy загружает
  `classpath*:ml/synthetic/*/request.json`, требует **ровно 6** resources и сравнивает
  точную пару **conversation + checklist**, а не только group ID или conversation.
  Maven пакует только `ml-service/tests/fixtures/*/request.json`, не reports/.
  Ни одна из двух пар demo не совпадает с шестью разрешёнными парами.
- Изменение одной checklist version/формулировки также не разрешает Java Live даже
  для прежней conversation. Нельзя подменять существующий fixture, чтобы пройти policy.
- Скомпилированных policy resources в `server/target/classes/ml/synthetic` в этом
  checkout нет: Java не собиралась и работающий JVM не инспектировался. Проверка Java
  здесь — source/config inspection, не новый runtime-тест. Исторический T14 отдельно
  фиксирует отказ 503 для dynamic criterion до ML HTTP.

Никаких allowlist, SyntheticPolicy, contracts, scoring или UI изменений не сделано.
Не предлагается отключать policy или выдавать ручную оценку за model-origin.

   к аккаунту. Бот приветствует, оператор сразу даёт инструкцию». Показать m0001,
   затем две строки m0003. Уточнить, что демонстрируется текст, не анализ аудио.
2. **20–40 с — v1.** Показать LOCAL_GREETING=no и его реальную цитату. Рядом

3. **40–65 с — новая рубрика.** В существующем редакторе заменить первый критерий
   на `DEMO_STEP_ORDER`, condition «оба шага и их порядок», binary, weight25,
   allow_na=false; сохранить новую версию 2. ID/key/version показываются явно.
   Не менять сообщения, Python-код или prompt. Число критериев остаётся 4, меняется
   состав набора answer IDs и правило интерпретации той же реплики.
4. **65–80 с — v2.** Показать предложенный/вручную введённый DEMO_STEP_ORDER=yes
   и цитату m0003. Объяснить: модель получает весь checklist как данные; offline
   проверка подтверждает передачу нового ID, но новый Live-ответ ещё не получен.
   N/A/CLARITY/GROSS остаются прежними; totals считает Java, не ML.
5. **80–90 с — история и честное ограничение.** Показать сохранённую v1 рядом с v2

## ML Demo Speech

Текст для выступления на 60–90 секунд при спокойном темпе. Новый demo показывается
как ручной offline-разбор с human ACCEPT Нуртаса. Он не зарегистрирован для
Python/Java Live inference; для этого требуется отдельное согласование.

Наша система помогает проверить качество работы оператора и понять причину каждой
оценки. ML-часть — отдельный сервис на Python и FastAPI. Он передаёт в Groq текст
диалога и полный чек-лист: критерии, допустимые ответы, шкалы и правила неприменимости.

Критерии не зашиты в код. Здесь мы вручную показываем один диалог с двумя версиями
чек-листа. Сначала проверяем приветствие, затем заменяем критерий на порядок двух
шагов. Правило оценки меняется через данные, без изменения кода ML. Ответы этого
нового примера подтверждены человеком; результатов Groq для него пока нет.

Каждый ответ сопровождается объяснением и дословной цитатой с идентификатором реплики.
Так можно проверить, на что опирается оценка. Совпадение цитаты проверяется строго,
а её смысловую уместность дополнительно оценивает человек. Java независимо проверяет
ответ и рассчитывает баллы по весам; модель итоговую сумму не назначает.

Мы принимаем диалоги на русском, казахском и английском. В прежнем прогоне оставались
ошибки языка объяснений. В Prompt v4 инструкции улучшены, но его Live-качество ещё
не измерено.

Для звонков оцениваем только расшифровку и порядок реплик. Интонацию и дикцию без
звука не оцениваем. Во внешнюю модель допускаются только согласованные синтетические
входы; реальные DEV/CONTROL и персональные данные мы туда не отправляем. Новый demo
остаётся offline до отдельного согласования.
